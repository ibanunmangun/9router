Todo 4 failure-path QA — proves the fetch/parse pipeline rejects garbage / non-200 responses.

============================================================
1) Bogus path probe — https://kenari.id/api/public/does-not-exist
============================================================
GET https://kenari.id/api/public/does-not-exist -> 200
Content-Type: text/html (3873 bytes) — SPA catch-all page, NOT JSON.

Observation: kenari.id serves an HTML SPA catch-all for unknown GET paths
(every bogus GET returns 200 text/html, including /api/public/pricing/nope,
/v1/nonexistent-route). So a GET-only status check is NOT a sufficient
liveness signal for this host.

Genuine non-200 observed (method mismatch, same routes):
POST https://kenari.id/api/public/pricing -> 405
POST https://kenari.id/v1/models          -> 405

Practical consequence for the fetch layer: response must be validated by
Content-Type / JSON parse, not just HTTP status — a 200 HTML page will fail
JSON.parse (see part 2).

============================================================
2) JSON.parse on deliberately truncated JSON (simulated partial download)
============================================================
Input (truncated mid-object, valid JSON prefix cut at byte 61):
  {"data":[{"id":"step-3-7-flash","pricing":{"input":4200000000

Output:
  THREW: SyntaxError - Expected ',' or '}' after property value in JSON at position 61 (line 1 column 62)
  threw = true
  process exit code = 0 (test asserted the throw)

Conclusion: JSON.parse rejects truncated/garbage payloads with SyntaxError —
the fixture-parse verification step cannot silently pass on corrupt data.

============================================================
3) Fixture parse verification (happy path)
============================================================
node -e "JSON.parse(require('fs').readFileSync('tests/fixtures/kenari/models.json'))"
  -> exit 0 (parses, no output)

node -e "JSON.parse(require('fs').readFileSync('tests/fixtures/kenari/pricing.json'))"
  -> exit 0 (parses, no output)

Both exit codes recorded above via "$LASTEXITCODE" in the invoking shell = 0.
